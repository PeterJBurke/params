# EECS 195 Drone Parameter Checker — GitHub Pages Agent Handoff

## Instructions for the coding agent

Build and publish a static, client-side website for UCI EECS 195 / ECPS 295, using the complete working prototype below as the starting point. Create `index.html` at the repository root and place the HTML code below in it. Use GitHub Pages **Deploy from a branch** (`main`, `/ (root)`) or GitHub Actions. No backend, API keys, analytics, or uploaded-file transmission is needed. The user will control their own GitHub repository and enable Pages.

### Requirements

- Read Mission Planner/ArduPilot `.param` files entirely in the browser. Show actual vs expected, pass/fail/missing/manual review, and export CSV.
- Support three profiles: ARC outdoor, 20-foot cage, 10-foot maiden flight.
- Support old and new aliases: `ARMING_CHECK=1` / `ARMING_SKIPCHK=0` (normal checks), `RTL_ALT=1500` / `RTL_ALT_M=15` (ARC), `RTL_ALT=200` / `RTL_ALT_M=2` (20-foot cage), `GPS_TYPE` / `GPS1_TYPE` where applicable.
- Do **not** infer actual firmware version solely from parameter names. Warn if both aliases occur and conflict.
- Validate numeric safety-related enum values against **official ArduPilot Copter 4.7 documentation and the installed firmware** before changing manual-review checks into automatic passes. In particular review `FS_THR_ENABLE` and `FENCE_ACTION`.
- Confirm the `ARMING_SKIPCHK` bitmask behavior and exact GPS-related exceptions against the official 4.7 documentation before recommending a 10-foot-cage bitmask.
- Preserve profile differences (ARC: RTL 15 m and fence enabled; 20-foot cage: RTL 2 m and fence disabled). The 10-foot checklist does not require the same GPS configuration as ARC.
- Include an obvious warning that a parameter checker cannot replace physical preflight, calibration, failsafe, fence geometry, battery chemistry, or flight testing.
- Add basic automated tests with fixture `.param` files covering 4.6-style, 4.7-style, missing parameters, conflicts, and incorrect values; test on mobile.
- Keep everything suitable for GitHub Pages: relative paths, no server routes, no build step required unless useful.

## CRITICAL: ArduPilot 4.6 versus 4.7 parameter nomenclature and units

**This is a central requirement, not a cosmetic change.** The course's original checker was written for older ArduCopter parameter names. The August 8, 2026 example `.param` file uses 4.7-style names. A checker that looks only for the old name will falsely mark a correct 4.7 file as missing or failing. Conversely, blindly comparing old and new numeric values without unit conversion can produce dangerously wrong conclusions.

| Course requirement | ArduCopter 4.6-style | ArduCopter 4.7-style | Interpretation |
|---|---|---|---|
| All normal pre-arm checks enabled | `ARMING_CHECK=1` | `ARMING_SKIPCHK=0` | **Logic inverted**: `ARMING_SKIPCHK` is a *skip-check bitmask*; zero skips none. Do not translate a nonzero bitmask by simply negating it. |
| ARC RTL altitude 15 m | `RTL_ALT=1500` (cm) | `RTL_ALT_M=15` (m) | **Scale conversion: divide old cm by 100.** |
| 20-foot cage RTL altitude 2 m | `RTL_ALT=200` (cm) | `RTL_ALT_M=2` (m) | **Scale conversion: divide old cm by 100.** |
| Primary GPS type | `GPS_TYPE` in some older files/instructions | `GPS1_TYPE` in the current course files | Handle alias for compatibility; confirm against installed firmware documentation. |

Other 4.7 migration examples outside the checker requirements include `LAND_SPEED` (cm/s) → `LAND_SPD_MS` (m/s), `PILOT_SPEED_UP` (cm/s) → `PILOT_SPD_UP` (m/s), and `WPNAV_SPEED` (cm/s) → `WP_SPD` (m/s). **Do not automatically add checks for these** unless they are part of the instructor's requirements. Their purpose here is to illustrate that 4.7 changes may involve both names and units.

### Required implementation behavior

1. Treat each requirement as a **canonical semantic value in canonical units**, e.g. `rtl_altitude_m = 15`, then normalize either parameter alias to it before comparison. Never compare `RTL_ALT=1500` directly to `RTL_ALT_M=15`.
2. Display the **actual parameter name, raw value, raw units, normalized value, and expected value** so students understand why a result passes or fails. Example: `RTL_ALT_M = 15 m` and `RTL_ALT = 1500 cm` should both pass the ARC profile.
3. For `ARMING_CHECK`, require `1` to mean all checks enabled; for `ARMING_SKIPCHK`, require `0`. **Do not accept `ARMING_CHECK=0` as enabling checks.** For the 10-foot cage, allow only instructor-approved, explicitly documented skip-check bitmasks; do not silently turn off all checks.
4. If a file has **both old and new aliases**, check each independently after conversion. Flag contradictory settings as a conflict, not as a pass just because one alias matches. Consider that stale aliases may remain in exported files, and ask for manual review rather than asserting both are active.
5. **Do not infer or assert the installed firmware version from names alone.** A file is not proof of which firmware is currently flashed; a ground station or migration process can affect representation. Describe the detected schema as `4.6-style`, `4.7-style`, `mixed`, or `unknown`, and label it as an inference. Offer a place to enter a confirmed firmware version.
6. Keep **firmware compatibility** distinct from **flight-profile requirements**. ARC needs 15 m RTL and geofence enabled; the 20-foot cage needs 2 m RTL and geofence disabled. These are intentional course differences, not firmware naming errors.
7. Unit-test both nomenclatures with equivalent and deliberately mismatched values, including `RTL_ALT=1500` vs `RTL_ALT_M=15`, `RTL_ALT=200` vs `RTL_ALT_M=2`, `ARMING_CHECK=1` vs `ARMING_SKIPCHK=0`, invalid `ARMING_CHECK=0`, missing aliases, and conflicting aliases. Use official ArduPilot 4.7 parameter documentation as the source of truth and record links/firmware versions in the repository.

**Important for the coding agent:** The prototype below already supports basic aliases, but does **not** fully implement the raw-units/normalized-units display, schema diagnostics, or nuanced conflict handling described above. Implement those improvements before treating it as production-ready. The old checker screenshot embedded in the course checklists shows `ARMING_CHECK` and `RTL_ALT` (cm); the updated checklist text uses `ARMING_SKIPCHK` and `RTL_ALT_M` (m). The website must not perpetuate that discrepancy.

### Deployment

1. Create a GitHub repository (for example `eecs195-parameter-checker`).
2. Save the code below as `index.html` in the repository root and commit to `main`.
3. In repository **Settings → Pages**, choose **Deploy from a branch**, branch `main`, folder `/ (root)`, and save.
4. Open the Pages URL displayed by GitHub (usually `https://USERNAME.github.io/eecs195-parameter-checker/`).
5. Link the existing UCI Google Sites page to that URL, or embed it if permitted.

### Current prototype limitations

The HTML below is a prototype, not an independently verified flight-safety tool. Some checks are deliberately manual review; do not remove that qualification without verifying official firmware enums and course policy. The prototype parser supports ordinary comma/space/tab-separated numeric parameter files, but needs additional tests for alternative formats, duplicate keys, and malformed uploads. The source is currently a single minified-style HTML file; refactor for maintainability if desired.
